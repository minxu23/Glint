## 1. 背景

`--verify` 会把 HEIF 里没地方放的 JPEG 段和 EOI 之后的数据逐条报成「丢失」
（`unportableSegments`，`Sources/Core/JPEGLayout.swift`）。用户看过真实照片里这些东西各是
什么之后决定：**没有价值的直接丢弃，不再报**。只改校验，不改转换。

后果要清楚：这些文件校验通过后，`--delete-original` 会删源。这是用户要的。

## 2. 交接方量到的事实（main = b0d110c）

样本来自用户的私有测试集，你拿不到；下面是结构事实，复现用 `Tests/fixture` 和
`Tests/mangle-tool`（可以加选项）。

| 样本 | 现在的报告 | 内容 |
|---|---|---|
| 富士 X100F | `丢失 APP2 段（FPXR，134/50/19582 字节）` 三行 | FlashPix 扩展。大段里嵌着一张 JPEG（相机的预览图），另两段是目录 |
| 某网图 | `丢失 APP12 段（Ducky，15 字节）` | `Ducky` + 一条记录：标签 1（保存质量）、长 4、值 80，再无别的记录。Photoshop「存储为 Web 格式」写的 |
| 微信导出 | `丢失 EOI 之后的 8 字节` | 恰好 `74 79 66 2D 00 00 00 00`（`tyf-` 加 4 个 0） |
| Snapseed 编辑过的华为 HDR 照片 | `丢失 APP2 段（urn:iso:std:iso:ts:21496:-1，32 字节）` | Snapseed 重存时扔了增益图，却保留了 MPF 索引和主图里的 ISO 21496 版本标记段；索引说第二张图在 812827 字节处，文件只有 659382 字节。源里没有增益图，转换没丢任何东西 |
| 华为 Pura 90 HDR 照片 | `丢失 EOI 之后的 1455836 字节（MPF 多图格式的附加图像）` | 尾部 = 190172 字节的 ISO 增益图（MPF 登记，类型码 **0x050000**）+ 1265664 字节华为私有块（`VLDMAGIC` 开头，MPF 没登记）。增益图**已经带进产物**：两边 ImageIO 都读得出 ISO 增益图，都是 1536×2048、像素格式 875704422 |
| 仓库里的 `test_pic/P1130939.JPG` | `丢失 EOI 之后的 845456 字节（MPF 多图格式的附加图像）`（selftest 7e 的断言） | 尾部 = MPF 登记的大尺寸预览图（类型码 0x010002，3328000 起 845023 字节）+ 前后的填充（自己核对填充的字节） |

最后两行的根因：`carriedTrailerRanges` 只认类型码 0 的 MPF 条目。新版 MPF（Exif 3.0 时代，
exiftool 叫 `Gain Map Image`）给增益图专门定了 0x050000，华为的 HDR 照片用的就是它，于是带过去
的增益图仍被算进丢失的字节，括号里的说明也错（大部分是 MPF 没登记的私有数据）。

## 3. 设计（已定）

### 3.1 不再报的（静默，不计入差异，与 `AROT\0\0` 同一待遇）

每一条都要窄：只认下面写的形状，差一点就照报。

1. **FlashPix 扩展**：APP2，内容以 `FPXR\0` 开头。全部不报（目录段和数据段都是）。
2. **Photoshop 的 Ducky 段**：APP12，内容以 `Ducky` 开头，后面的记录（2 字节标签、2 字节长度、
   数据，大端；标签 0 或段尾结束）能完整解析，且**只有标签 1（保存质量）**。有标签 2（注释）、
   3（版权）或别的标签，或者解析不通，照报。
3. **ISO 21496-1 版本标记段**（`isISOGainMapVersionSegment`，恰好 32 字节）：**一律不报**。它只有
   版本号；增益图本身丢没丢，由尾部记账和辅助图的键比对负责（源里有增益图而产物里没有时，
   尾部的增益图字节没人认领，照报）。`isoGainMapCarried` 参数若因此不再需要就删掉。多出字节的照报
   （现有断言保留）。
4. **微信的尾部标记**：EOI 之后、去掉已认领的范围后，剩下的字节**恰好**是
   `74 79 66 2D 00 00 00 00`，不报。多一个字节、少一个字节、后 4 字节不全是 0，照报。
   与填充的关系：只认这 8 字节本身，前后再有填充也照报（不要为此写通用规则）。
5. **MPF 登记的大尺寸预览图**：MPF 条目类型码 0x010001 或 0x010002，范围整个落在尾部、不与别的
   已认领范围重叠、恰好是一张完整的 JPEG（`standaloneJPEGSize` 不是 nil）。这是主图的缩小拷贝，
   与 EXIF 缩略图「有意不报」同理。条件不满足的照报。

### 3.2 增益图的尾部记账

`carriedTrailerRanges` 认类型码 0 **或 0x050000**，其余条件不变（完整 JPEG、宽高与两边都有的
辅助图匹配、每张辅助图只认领一个条目）。0x040000（Exif 3.0 的 Original Preservation Image，
编辑前的原图）**不认**，照报。

### 3.3 尾部那一行的写法

记 M = 尾部总字节，K = 已搬进产物的辅助图字节，P = 不报的预览图字节（3.1 第 5 条），
R = M − K − P。R 里只要有非填充字节（0x00/0xFF 以外）且不是 3.1 第 4 条的情形，就报一行：

- K、P 都是 0：R 全部落在 MPF 登记的条目范围内（填充不算）→ `丢失 EOI 之后的 R 字节（MPF 多图格式的附加图像）`；
  否则 → `丢失 EOI 之后的 R 字节`。
- K 或 P 不是 0：`丢失 EOI 之后的 R 字节（尾部共 M 字节，其中 …）`，「其中」后面按出现的列
  `K 字节是已搬进产物的辅助图像`、`P 字节是 MPF 登记的预览图，不需要带`，两项都有时用「，」连。

K > 0、P = 0 时与现在的写法逐字相同，现有断言不用改。

华为那张应得：`丢失 EOI 之后的 1265664 字节（尾部共 1455836 字节，其中 190172 字节是已搬进产物的辅助图像）`。

## 4. 验收标准

1. `make test` 全绿；各计数与 b0d110c 的差别逐条说明。
2. 每条新规则都有一对断言：认得的形状不报、差一点的照报。至少：
   - FPXR 不报；APP2 `FPXQ\0…` 或 APP3 `FPXR\0…` 照报。
   - Ducky 只有质量不报；Ducky 带注释记录照报；Ducky 记录长度越界照报。
   - 32 字节版本标记段在源里没有增益图时不报（现在 selftest 7f「只有标记段」那条反过来，并说明
     为什么改）；33 字节的照报。
   - `tyf-`+4 个 0 不报；`tyf-` 后 4 字节有非 0、或 9 字节的照报。
   - 类型码 0x050000 的增益图带过去了不计入丢失（要造出这样的样本：MPF 条目类型码改成 0x050000，
     可给 mangle-tool 加选项）；宽高对不上照报；类型码 0x040000 照报。
   - 0x010002 的完整 JPEG 预览图不报（`P1130939.JPG` 现在应该校验通过，selftest 7e 那条反过来）；
     预览图后面另有非填充数据照报，且行里的 P、R 对。
   - 3.3 的几种写法各有一条（单测里直接测 `unportableSegments` 即可）。
3. 你自己做变异，每条规则至少一个，全部要红：把 3.1 的五条各自放宽成「同标记全不报」或删掉、
   把 0x050000 去掉、把「只有标签 1」去掉。报告里列变异和失败的断言。
4. 零噪声：转换不变——`test_pic/` 与夹具的产物与 b0d110c 逐字节相同（串行跑，机器上没有别的
   转换）；`--verify` 输出与 b0d110c 的差别只能是上面这些行消失或改写。
5. 只改 `JPEGLayout.swift` 和（如有需要）`MetadataDiff.swift` 里传参的地方、测试、mangle-tool、README。
