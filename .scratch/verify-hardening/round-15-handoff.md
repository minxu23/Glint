# 第 15 轮交接稿：把辅助图像搬进产物

工作规则、长期要求、变异与 mtime 陷阱的注意事项，全部沿用
[`round-12-handoff.md`](round-12-handoff.md) 的第 0 节，先读那一节。

这一轮是加功能，不是修缺陷：现在辅助图像（HDR 增益图、深度图、视差图、人像蒙版等）
转换时会丢，`--verify` 如实报出、源文件保留。用户决定把它们搬过去。

## 交接方量到的事实（main = 483e440）

### 1. 能搬，而且第二遍不会弄丢

在拷贝里照 `encodeHEIF` 的两遍写法做了实验（工具见 `round-15-repro/auxcarry.swift`）：
第一遍 `AddImageFromSource` 之后，对源里每一种辅助图调一次
`CGImageDestinationAddAuxiliaryDataInfo`。结果：四种合成样本和四张真实 HDR 照片，
第一遍的产物里都有辅助图；第二遍 `CopyImageSource` 之后**仍然在**。

### 2. 数据保真度分两类

| 类型 | 像素数据 | 附带元数据 |
|---|---|---|
| 深度图、视差图（32 位浮点） | 与源逐字节相同 | 保留 |
| 人像蒙版、增益图（8 位） | **有损**：有纹理的合成样本约六成像素有变化，最大差 7/255；每行字节数也变了（128 → 160，多了对齐填充） | 真实样本上保留（见下） |

8 位的那两类被有损重新编码，和主图一样（README 本来就写着"HEIF 编码是有损的"）。可以
接受，但要写明，而且测试里的保真度断言要按类型分开写。

### 3. 真实 HDR 照片：搬过去之后 HDR 是对的

度量方法（`round-15-repro/hdrinfo.swift`）：按 HDR 方式解码
（`kCGImageSourceDecodeRequest: kCGImageSourceDecodeToHDR`），画进扩展线性 sRGB 的浮点
位图，看"内容余量"（`CGImage.contentHeadroom`）和最亮像素相对 SDR 白的倍数。

| 样本 | 源：余量 / 最亮 | 现行产物 | 搬了增益图的实验产物 |
|---|---|---|---|
| 苹果旧格式增益图 | 8.00 / 4.16 | 1.00 / 1.10 | 8.00 / 4.15 |
| 苹果新格式增益图 | 4.53 / 2.61 | 1.00 / 1.10 | 4.53 / 2.60 |
| 安卓 Ultra HDR（两张） | 4.61 / 4.63、6.31 / 5.94 | 1.00 / 1.02 | 4.61 / 4.62、6.31 / 5.97 |

增益图附带的元数据也都在：苹果的 `HDRGainMap:HDRGainMapVersion`、
`HDRGainMap:HDRGainMapHeadroom`，ISO 增益图的 `HDRToneMap:*`。

**注意一个假象**：合成的增益图样本（不带真实元数据）搬过去后 ImageIO 报"没有附带元数据"
——它本来只有一个 `iio:hasXMP` 占位标签。别据此得出"元数据会丢"的结论，也别拿这种样本
当元数据保留的见证。

四张真实样本在交接方的临时目录里，**只供你量，不许复制进仓库**（其中两张来自
`google/libultrahdr` 的测试数据，许可不明确；另两张是 CC-BY-4.0）：

### 4. 搬过去之后，现行校验器还会报什么

用现行的 `metadataDiff` 比（源, 实验产物）：

- 那一串 `{FileContents}/Images[0]/AuxiliaryData[…]/…` 和 `DerivationDetails[…]` 的"丢失"
  **全部消失**——现有的键空间比对就能认出它们在。
- **剩一条误报**：`丢失 EOI 之后的 N 字节（MPF 多图格式的附加图像）`。辅助图在 JPEG 里
  就存在 EOI 之后（MPF 登记），现在搬过去了，这条不该再报。
- **对照**：`test_pic/P1130939.JPG` 的 EOI 之后是一张 845456 字节的大尺寸预览图，不是辅助
  图，ImageIO 不认、搬不走。它那条**必须照旧报**。
- 安卓那张真实照片另报了 5 条 `{FileContents}/Images[0]/ThumbnailImages[0]/…`
  （`Height`、`Orientation`、`ThumbnailOffset`、`ThumbnailSize`、`Width`）。

## 要做的

### A. 把辅助图搬过去

在 `encodeHEIF` 的第一遍里，把源里存在的每一种辅助图加进产物。类型要列全
（`kCGImageAuxiliaryDataType*` 的全部成员，包括各种语义分割蒙版和两种增益图），不要只列
量过的那几种。某一种加不进去时不要让整次转换失败——校验会把它报成"丢失"，那就是正确
的结果。

量一下并写进报告：`kCGImageDestinationLossyCompressionQuality` 对 8 位辅助图的编码质量
有没有影响。

### B. 尾部数据的记账

"EOI 之后的字节"里，属于已经搬过去的辅助图的那部分不再报丢；其余照旧报。判据由你定，
但要满足下面三条，并且**拿不准就报**：

1. 辅助图全部搬过去的文件（合成样本、四张真实 HDR 样本）：不再报尾部丢失；
2. `P1130939`：照旧报那 845456 字节；
3. 尾部既有辅助图又有别的东西的文件：别的那部分必须报出来（报成整段也可以，漏报不行）。

### C. `{FileContents}` 里的缩略图键

上一轮的决定是"缩略图有意忽略"（README 的忽略清单里有，理由是它是像素的派生物），但
实现只覆盖了一部分暴露方式。`{FileContents}/Images[n]/ThumbnailImages[…]/…` 这一组键
按同一条策略处理。先量：这组键在哪些样本上出现、有哪些子键，再按**完整键路径**的规则
去忽略（项目的既有约束：不用子串匹配，见 README 对易变键的说明）。`test_pic/` 两张照片
转换前后的输出不得因此改变。

### D. 文档

README：`## 已知限制` 里"深度图、视差图、HDR 增益图等辅助图像不会保留"按做完后的实际
行为改写（哪些逐字节保留、哪些有损、搬不过去时会怎样）；`## 保留了哪些元数据` 和
`## --verify 到底比什么` 相应补上；缩略图那条把 `ThumbnailImages` 这组键写进去。只写
现在的行为。

## 验证方案

见证样本要在仓库内自足地造（扩展 `Tests/fixture.swift`，用
`CGImageDestinationAddAuxiliaryDataInfo` 往 JPEG 里加辅助图；`round-15-repro/` 里的工具
可以参考写法，但测试不得依赖它们，也不得依赖真实样本）。

1. **每种辅助图一张合成样本**（至少：深度图、视差图、人像蒙版、带真实元数据的苹果增益图
   ——元数据要含 `HDRGainMapVersion` 和 `HDRGainMapHeadroom`；ISO 增益图如果造得出来也加）。
   内容要有纹理，不能是纯色（纯色看不出有损，也看不出数据被换掉）。逐张断言：
   - 产物里有同一类型的辅助图，尺寸和像素格式相同；
   - 浮点类型：数据逐字节相同；8 位类型：去掉行尾填充后与源的最大差不超过一个你量出来
     并写明的上界；
   - 附带元数据的标签集合与源相同（增益图那张尤其要断言版本和余量两个标签的值）；
   - `✓ 元数据校验通过`，`--delete-original` 删源。
2. **增益图样本的 HDR 度量**：产物按 HDR 解码的内容余量与源相同。
3. **尾部记账**：`P1130939`（不截尾）仍报出那条 845456 字节；一张"辅助图 + 额外尾部数据"
   的样本（可以用 `mangle --append` 在合成样本后面追加）仍报出尾部丢失。
4. **变异**（每条都要亲眼看红）：
   - 去掉搬运 → 第 1、2 项变红；
   - 尾部记账改成"有辅助图就一律不报" → 第 3 项的后一张变红；
   - 尾部记账改成"一律不报" → `P1130939` 那条变红；
   - 缩略图键的忽略去掉 → 你为 C 加的断言变红。
5. **真实样本**（只量、不入库、不进测试）：四张各转一遍，报告里给出校验输出和 HDR 度量
   （源 vs 产物）。目标是四张都只剩"确实搬不走的东西"；还剩什么逐行说明。
6. **零噪声**：六种夹具（默认、`--no-exif-offset`、`--lossy`、`--cmyk`、`--rich-xmp`、
   `--extended-xmp`）和 `test_pic/` 两张真实照片的 `--verify` 输出不得多出任何一行；
   没有辅助图的输入，产物必须与修改前**逐字节相同**。
7. **健壮性**：辅助图数据来自源文件，尾部记账要解析 MPF——偏移和长度都不可信。截断的、
   MPF 条目指向文件外的、条目数离谱的，都不能崩，也不能因此把该报的尾部丢失吞掉。
