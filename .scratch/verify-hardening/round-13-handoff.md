# 第 13 轮交接稿：剩下的静默缺口

工作规则、长期要求、变异与 mtime 陷阱的注意事项，全部沿用
[`round-12-handoff.md`](round-12-handoff.md) 的第 0 节，先读那一节。本稿只有一批。

## 背景

第 12 轮把这三样写进了 README 的"已知限制"，注明"会丢，`--verify` 不报"：

1. Windows 写的 XP 标签（EXIF IFD0 的 `0x9C9B–0x9C9F`）和评级（`0x4746`、`0x4749`）；
2. APP13 里除 IPTC（`8BIM 0x0404`）以外的 Photoshop 资源块；
3. EXIF IFD1 缩略图。

用户决定把这个缺口关掉。交接方在当前 main（`c9321f6`）上复现了前两样，并量了真实
照片里的情况，结论是三样的处理方式不同。

## G1 XP 标签与评级：报，但要过"等价字段承载"这一关

- **现象（已复现）**：用 `round-12-repro/jt.py xp` 造的样本，`XPComment`、`XPKeywords`、
  `XPTitle` 的 UTF-16 文本在源里各出现 1 次，HEIC 里 0 次（UTF-8 形式也是 0 次）；
  `✓ 元数据校验通过`，`--delete-original` 删了源。
- **必须知道的事实（已量）**：`test_pic/IMG_1225.JPG` 的 IFD0 里就有
  `XPAuthor = "Zhang San;Li Si"`，同时标准字段 `Artist (0x013B)` 也是 `"Zhang San;Li Si"`。
  转换后产物里 `{TIFF}/Artist` 和 `XMP/dc:creator[0]` 都是这个值。Windows 写 XP 标签时
  通常同时写一份标准字段。所以**不能见到 XP 标签就报丢**——那会让这张真实照片多出一条
  误报。
- **修改方向**：从源文件原始字节读这些标签（`TIFFStructure` 已有 IFD 遍历；XP 标签是
  UTF-16LE、以 NUL 结尾的字节串）。判据沿用项目已有的规则——README 对 IIM 日期写的是
  "等价字段确实带着同一个值，不是等价字段存在"。给每个标签一张目标侧的等价字段表，
  值对得上才算承载，否则报"丢失"。等价表以实测为准，交接方的起点建议是：

  | 源标签 | 目标侧可承载它的字段 |
  |---|---|
  | `XPTitle 0x9C9B` | `{TIFF}/ImageDescription`、`XMP/dc:title[*]`、`XMP/dc:description[*]` |
  | `XPComment 0x9C9C` | `{Exif}/UserComment`、`XMP/exif:UserComment[*]` |
  | `XPAuthor 0x9C9D` | `{TIFF}/Artist`、`XMP/dc:creator[*]` |
  | `XPKeywords 0x9C9E` | `XMP/dc:subject[*]`、`{IPTC}/Keywords[*]` |
  | `XPSubject 0x9C9F` | 没有公认的等价字段；找不到就报 |
  | `Rating 0x4746` | `XMP/xmp:Rating` |
  | `RatingPercent 0x4749` | `XMP/MicrosoftPhoto:Rating` |

  多值字段的写法不同（XP 用分号分隔的一个串，XMP 是数组；`Artist` 里的分号可能被
  ImageIO 拆成多个 `dc:creator`）——先量 ImageIO 实际怎么写，再定怎么比。**宁可多报**：
  拿不准是否等价的，报。
- **先量再定的一件事**：`Rating (0x4746)` 在 ImageIO 的源视图里有没有对应的键？如果有
  而且会被搬到目标，现有的键空间比对已经管着它，就不要再加一条重复的；如果没有，
  按上表处理。把量到的结果写进报告。
- **验证方案**：
  - 一张只有 XP 标签、没有对应标准字段的样本：每个标签各报一条，`--delete-original`
    保留源；
  - 一张 XP 标签与标准字段同值的样本（即 `IMG_1225` 的情形）：不报；
  - 一张 XP 标签与标准字段**不同值**的样本：报；
  - 变异一：让读 XP 标签的函数返回空 → 第一、三张变红；
  - 变异二：把"值对得上"改成"等价字段存在就算" → 第三张变红。
  - 样本要在仓库内自足地造（扩展 `Tests/mangle/` 或 `Tests/fixture.swift`，不能用 Python）。
    造 IFD 条目要自己拼字节，`round-12-repro/jt.py` 的 `xp` 分支可以参考拼法。

## G2 Photoshop 的其它资源块：一条汇总行

- **现象（已复现）**：往默认夹具的 APP13 里追加一个 `8BIM 0x0BB7` 资源（内容带标记串），
  `✓ 元数据校验通过`，`--delete-original` 删了源，标记串在 HEIC 里出现 0 次。
- **必须知道的事实（已量）**：默认夹具的 APP13 本来就有两个资源：`0x0404`（IPTC，已有
  规则管着）和 `0x0425`（IPTC 摘要，是 `0x0404` 的校验和，派生数据）。两张真实照片
  没有 APP13。
- **修改方向**：列出 APP13 里的 8BIM 资源，除去已有规则管着的和纯派生的，剩下的合成
  **一条**汇总行（参照现有 MakerNote 汇总行的做法：一行，写个数和资源 ID），不要每个
  资源一行——Photoshop 存出来的 JPEG 常带十来个资源。排除清单的起点建议：
  `0x0404`（IPTC）、`0x0425`（IPTC 摘要）、`0x0409` 与 `0x040C`（缩略图，理由同 G3）。
  其余一律进汇总行，不要再往排除清单里加"看起来不重要"的 ID——拿不准就报。
- **验证方案**：追加 `0x0BB7` 的样本报出汇总行（含这个 ID）并保留源；默认夹具不新增
  任何行；变异：让资源清单返回空 → 变红；变异：把 `0x0BB7` 加进排除清单 → 变红。

## G3 EXIF 缩略图：不加检测，改写成"有意忽略"

- **事实（已量）**：两张真实照片的 IFD1 都有缩略图（4867、4779 字节），产物里没有内嵌
  缩略图。任何相机直出的 JPEG 都带一个。
- **决定**：缩略图是从像素派生的预览，不是照片内容，和 README 已经有意忽略的"文件
  体积、压缩方式"同类。报它会让几乎所有真实照片校验不过。所以**不做检测**。
- **要做的只有文档**：README 里把它从"已知限制 · 校验不报"那一条里拿出来，写进
  `## --verify 到底比什么` 的"有意忽略"清单，给出上面的理由。Photoshop 资源里的缩略图
  （`0x0409`、`0x040C`）同理，一并写明。

## 零噪声（硬要求）

动手前把这些样本的校验输出存成基线：默认、`--no-exif-offset`、`--lossy`、`--cmyk`、
`--rich-xmp`、`--extended-xmp` 六种夹具，以及 `test_pic/` 两张真实照片（先拷贝再转）。
改完逐行对比，**不得多出任何一行**。`IMG_1225` 尤其要看：它的 XPAuthor 与 Artist 同值，
必须不报。新增行说不清来历的就是误报，修掉，不要解释掉。
